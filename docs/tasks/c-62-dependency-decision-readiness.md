## Code-truth boundary

- `inventory-business-documents.service.ts` finalizes quantity effects in a caller-owned Inventory transaction, but number allocation is a separate, non-composable transaction. Its `accountingPostDocument` locks header and valuation keys and writes `accounting_posted`/actor/time **without** invoking Accounting, an operation key, voucher or posting reference. Repeated calls return the existing document. This is a **production gap**, not merely documentation drift; the C-61 docs already warn of it. Do not interpret the flag as PO-10 proof. Domain transition `operational → accounting_posted → immutable`; cancel is pre-accounting only; direct material edit after post is rejected. `isAccountingEligible` checks operational/priced/non-stale; service additionally locks relevant valuation keys before transition. Eligibility is not authority, mapping readiness, or successful posting.
- `accounting.module.ts` exports `AccountingDocumentsService` but NOT `PostingService` (in-module). `AccountingDocumentsService.createDocument` accepts a system origin/source and balanced caller-supplied account lines; it requires `Accounting.Document.Create`, organization scope, financial area, usable accounts and a key; `finalizeDocument` requires `Accounting.Document.Finalize` and calls internal `postVoucher`. Create may result in draft or temporary according to document-type settings; creation does not guarantee finalized ledger. Accounting has durable operation-key/request-hash replay and a transaction for its own posting, but its service is NOT a source-facts-to-mapping integration contract. The smallest *existing exported* seam is this document service; there is **no suitable public Inventory-facts posting service**. Calling it directly would force Inventory to choose accounts and orchestration, violating PO-01. Do not export internal repositories or reuse the existing API as the new contract by implication.
- Inventory can safely expose via a future public application contract an organization-scoped approved document identity/type/number/date/status, line-to-movement IDs (including both transfer legs), authoritative movement quantity/value/unit cost and valuation state/stale status, valuation run/basis references available in its valuation repositories, and source actor/timestamps. It must assemble an immutable-at-posting snapshot with evidence under proper cost authorization; Accounting must not read Inventory tables. Do not treat the cost-redacted document DTO as sufficient posting evidence. Inventory return lines link to basis movements; the Inventory document does not accept a Purchase Return commercial amount (`inventory-business-document.ts`); an agreed amount requires an authorized separate source/contract before variance can be detected.
- Code/documentation discrepancy: legacy Item/Warehouse negative-stock override API remains despite OD-VAL-17 hard-block policy (also recorded in OQ-24); not a reason to implement Accounting or change stock behavior here. C-61 STATE section calls C-61 working-branch/pending despite actual merge #130: historical status wording drift, not a new decision. No production behavior changed.

## Atomicity and lifecycle decision space

Same-process Modular Monolith and Prisma transactions make a shared DB transaction technically conceivable, **not decided**: existing Inventory transaction locks header/key rows; Accounting owns its posting transaction and numbering may allocate independently. Nested non-composable transactions cannot simply be wrapped. Alternatively commit Inventory operational fact first then run an independently durable Accounting operation with explicit pending/failed/refused state; or invoke Accounting inside a caller-owned transaction with refactored transaction ownership. Both require a public transaction-safe contract and lock ordering. A synchronous call alone guarantees neither shared commit nor durable retry. An in-memory event bus cannot be the primary posting path under PO-02 and cannot recover after restart.

Inventory commit + Accounting refusal: operational document may remain operational, but whether it is retryable, blocked, or compensated is Owner policy. Accounting commit + caller timeout: query durable operation key/result before doing anything new; never infer failure from timeout. Retry same key/hash returns the original result, different hash conflicts (PO-09); survive process restart in persisted unique operation record linking document, voucher and result. The authoritative success evidence is an Accounting-owned persisted operation/final voucher plus Inventory linkage, **not** an Inventory flag or emitted event. Whether a temporary voucher counts as `accountingPosted` and whether a failed attempt changes status are business choices; hash algorithm, transaction plumbing and lock ordering are engineering design after policy. Failed attempt must not be represented as posted by assumption. Repeated request on already posted source must reconcile against durable operation evidence; new key must not create a second ordinary voucher (PO-04/10).

## Proposed decision contract shape (NOT an API)

A command carries source organization/legal entity, approved document type/id, stable operation key, canonical request version/hash, actor kind/id/delegation, immutable valuation evidence and policy context. Accounting returns a durable operation ID, voucher ID/phase, outcome (final/temporary/refused), source reference and replay indicator; domain refusals return typed reasons. Inventory persists/derives posting reference and changes `accountingPosted` only on the Owner-defined successful phase. Authorization and organization/area checks rerun at invocation (not merely at eligibility); revoked permission must not be bypassed by a cached eligible flag. Exact key namespace/hash fields, failure status and finalization authority require decisions below.

### OD-01 technical feasibility finding — NOT CLEANLY FEASIBLE in current code

`InventoryBusinessDocumentsRepository.withTransaction` creates its own Prisma interactive transaction and hands a `DocTxClient` to Inventory. `AccountingDocumentsRepository.createChecked` and `finalizeChecked` each acquire a Prisma client and start **their own** `$transaction`; `PostingService.postVoucher` calls that repository's finalization transaction rather than accepting a caller transaction. `AccountingDocumentsService.createDocument` may allocate a number via the separate Numbering authority before calling `createChecked`; Inventory finalization likewise allocates outside its transaction. Existing Accounting operation-key persistence is within its own write transaction, not the Inventory transaction. Inventory Accounting Post locks the document header and valuation state rows in its transaction; Accounting locks period/area/accounts/document/projection in its own prescribed order. Calling the exported service inside Inventory's transaction therefore produces separate commits, not atomicity; nested transactions, raw cross-module table access or passing an uncontracted client would be unsafe. Number allocation already has explicitly non-rollback behavior and cannot be equated with voucher/GL atomicity.

**Technical Feasibility Gate — Pending:** this is a finding about the *current* seam, not proof that a clean redesigned caller-owned shared contract is impossible. Before implementing, document whether a public Accounting contract can safely accept a shared transaction while retaining module ownership, period/account locks, idempotency, numbering semantics and recovery. If cleanly feasible choose atomic A; otherwise choose Owner-approved durable pending/two-phase B. No third architecture. Capture lock-order and timeout/retry design and review before production work. Draft mode additionally separates creation from later human finalization: the first operation can be atomic with draft creation, but the later finalization cannot be the same transaction. Never set `accountingPosted` for a draft. A cancelled draft leaves audit evidence and no final GL effect.

### C-62 implementation architecture summary (OD-01 verdict & durable operation model)

1. **OD-01 Verdict — Durable Two-Phase (B):** Single cross-module atomic transaction is not cleanly feasible without cross-module lock inversion and redesigning external numbering/accounting transaction ownership. System implements durable two-phase with recoverable PENDING state and explicit immutable snapshot.
2. **Independent Operation Identities:** Posting (`action = 'accounting_post'`) and draft cancellation (`action = 'accounting_post:cancel'`) are distinct durable operations with separate operation keys, request hashes, actors, timestamps, and lifecycle states in `inventory_accounting_posting_operations`.
3. **Posting Operation Invariance:** A posting operation never transitions to `CANCELLED`; its `DRAFT_CREATED` state remains the immutable audit record of the draft it produced. Draft cancellation creates an independent cancellation operation that reaches `CANCELLED`.
4. **Idempotency & Replay:** Both posting and cancellation enforce OD-06: same operation key + same canonical request replays/converges; same key + different request yields 409 Conflict.
5. **Snapshot Recovery Authority:** Recovery of a PENDING posting reconstructs the request strictly from the immutable Posting Snapshot (OD-05), ensuring that subsequent mutable Inventory state changes cannot alter the historical Accounting intent.
6. **Cancellation Recovery:** Cancellation is crash-safe across all boundary phases: recovers safely whether Accounting draft exists, was already deleted, or if document projection lagged operation commitment.
