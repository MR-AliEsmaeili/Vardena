## 1. Deep Reconciled Analysis: Base Chart / OQ-25 Gate

### 1.1 The Four Invariants (Verified in Code on `main`)

| Invariant       | Principle                               | Implementation Evidence on `main`                                                                                                                                                                   | Verification Status                       |
| --------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| **Invariant 1** | **Template identity ≠ Ledger identity** | `accounting.base_chart_template_nodes` holds template definitions; `accounting.accounts` holds tenant organization ledger accounts. Ledger entries reference only `Account.id`.                     | **VERIFIED IN CODE (Task 23)**            |
| **Invariant 2** | **Adoption = Copy**                     | `BaseChartAdoptionsService.adoptBaseChart` copies published template nodes into independent `Account` rows for the organization. Later template modifications do NOT mutate adopted accounts.       | **VERIFIED IN CODE (Task 23)**            |
| **Invariant 3** | **Posting = Leaf-only**                 | Posting operations (`AccountingDocumentSupport`, `PostingService`) enforce that journal voucher lines only post to leaf accounts (`isPostable = true` with zero child accounts).                    | **VERIFIED IN CODE (Tasks 10.8, 19, 23)** |
| **Invariant 4** | **Aggregation = Read-time**             | Parent/group level balances are dynamically aggregated during read queries (`AccountingReadQueryRepository`, `ChartTreeService`, `TrialBalanceService`). No synthetic parent ledger postings exist. | **VERIFIED IN CODE (Tasks 18, 19)**       |

### 1.2 Strict Separation of the Six Base Chart Layers

```text
[1. Mechanism]  ──▶  [2. Template Entity]  ──▶  [3. Content (OQ-25)]
   (Merged)               (Merged)                  (0 ROWS / OPEN)
                                                           │
                                                           ▼
[6. Posting Behavior] ◀── [5. Ledger Accounts] ◀── [4. Org Adoption]
   (Leaf-only)              (Tenant-scoped)           (Copy action)
```

1. **Base Chart Mechanism:** Merged in Task 23 (controllers, services, repositories, validation, adoption copy transaction).
2. **Base Chart Template:** Prisma schema models exist (`BaseChartTemplate`, `BaseChartTemplateVersion`, `BaseChartTemplateLevel`, `BaseChartTemplateNode`, `BaseChartAdoption`).
3. **Base Chart Content:** **NOT IMPLEMENTED** (0 template node rows in migrations/seeds; standard Iranian SME chart tree is unapproved; gated by OQ-25).
4. **Organization Adoption:** API surface exists (`POST /api/v1/accounting/adopt-base-chart`).
5. **Ledger Accounts:** Tenant accounts in `accounting.accounts`.
6. **Posting Behavior:** Atomic, leaf-only journal entries in `accounting.ledger_entries`.

> **Critical Rule:** The existence and technical readiness of the Base Chart _mechanism_ does NOT imply that Base Chart _content_ is approved. Base Chart content remains decision-blocked by **OQ-25**.

> **OD-27-02 Update (2026-09-27, Task 28 follow-up — DECIDED):** The Owner explicitly decided that **the MVP requires the Base Chart mechanism but does not require a concrete Base Chart content set**. The mechanism/capability (layers 1, 2, 4, 5, 6 above, plus the Task 21 governance baseline) is MVP scope and must be provided and retained. The concrete content set (layer 3) is **not** MVP-required and must not be introduced by implementation inference — layer 3 stays at 0 rows / OPEN unless and until a separately approved content artifact exists. This decides the MVP-scope sub-question only; it does not close OQ-25 and does not reinterpret Task 21 or Task 23.
