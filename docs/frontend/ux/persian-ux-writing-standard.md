# FE-UX-02 — استاندارد نگارش تجربه کاربری فارسی وردنا

**وضعیت:** READY FOR REVIEW — قرارداد پیشنهادی رسمی نگارش UX
**تاریخ:** 2026-09-29
**دامنه:** متن کاربرمحور در رابط وب وردنا؛ بدون تغییر در کد، API یا پایگاه داده
**اسناد حاکم:** قرارداد API و دامنه، پیاده‌سازی موجود، `docs/frontend/standards.md` نسخه ۲.۲، سپس FE-UX-01 و این سند

## 1. هدف و واژگان وضعیت

این سند زبان رسمی رابط فارسی وردنا را تعیین می‌کند. هر پیام، در صورت ارتباط، باید به ترتیب به این پرسش‌ها پاسخ دهد:

1. چه اتفاقی افتاد؟
2. چرا اتفاق افتاد؟
3. کاربر اکنون چه کاری می‌تواند انجام دهد؟

در این دو سند FE-UX-02، وضعیت‌ها چنین‌اند:

| برچسب | معنی |
| --- | --- |
| `CURRENT` | اکنون در رابط فرانت‌اند قابل مشاهده و قابل استفاده است. |
| `SUPPORTED` | قرارداد/endpoint بکند وجود دارد، اما ممکن است UI تولیدکننده آن هنوز ساخته نشده باشد. |
| `CONTRACT GAP` | UX مطلوب به داده، کد خطای ماشینی، endpoint یا قرارداد بکندِ موجود دسترسی ندارد. |
| `FUTURE PRODUCT DECISION` | تصمیم محصول/حسابداری/حقوقی/معماری هنوز گرفته نشده است. |

`SUPPORTED` به معنی «در رابط فعلی موجود» نیست. هیچ مثال این سند به‌تنهایی قابلیت محصول ایجاد نمی‌کند.

## 2. لحن و اصول نگارش

### 2.1 لحن رسمی، محترمانه و مستقیم

- خطاب مستقیم با `شما` و فعل رسمی: `لطفاً دوباره تلاش کنید.`
- پیام، کاربر را مقصر معرفی نمی‌کند.
- جمله کوتاه، معلوم و عملیاتی است؛ از تعارف، شوخی و لحن محاوره‌ای پرهیز می‌شود.
- نام عمل و نتیجه به‌صراحت گفته می‌شود؛ «موفقیت» یا «خطا» بدون نام عمل کافی نیست.
- دلیل فقط وقتی گفته می‌شود که از قرارداد معتبر به دست آمده باشد؛ دلیل حدسی ممنوع است.
- پیام امنیتی نباید وجود موجودیت خارج از دامنه سازمان را افشا کند.

| نامطلوب | مطلوب |
| --- | --- |
| `یه مشکلی پیش اومد` | `در دریافت اطلاعات مشکلی پیش آمد. لطفاً دوباره تلاش کنید.` |
| `شما اشتباه وارد کردید` | `مبلغ باید بزرگ‌تر از صفر باشد.` |
| `خطایی رخ داد` | `ذخیره سند انجام نشد. لطفاً دوباره تلاش کنید.` |
| `Access denied` | `شما مجوز مشاهده این بخش را ندارید.` |

### 2.2 ایجاز و ترتیب اطلاعات

1. نتیجه یا مانع؛ 2. دلیل قابل فهم؛ 3. راه بازیابی. یک پیام معمولاً یک تا دو جمله است. جزئیات پشتیبانی مانند کد پیگیری پس از پیام اصلی می‌آید، نه در عنوان.

- عنوان: نام وضعیت یا عمل، بدون نقطه؛ مانند `دریافت گزارش انجام نشد`.
- بدنه: دلیل و اقدام بعدی؛ با نقطه کامل می‌شود.
- دکمه: فعل یا عبارت عملیاتی؛ بدون نقطه و بدون `بله/خیر`.

## 4. املا، فاصله‌گذاری و نشانه‌گذاری

- فارسی معیار و نیم‌فاصله: `می‌شود`، `نمی‌تواند`، `موردنیاز`، `انتخاب‌شده`، `مهروموم‌شده`.
- `ی` و `ک` فارسی (`ی`، `ک`)؛ نویسه عربی `ي` و `ك` در متن UI ممنوع.
- پایان جمله با نقطه فارسی/متعارف `.`؛ در پرسش مستقیم `؟`.
- ویرگول فارسی `،` و نقطه‌ویرگول `؛` به‌کار می‌رود. در الگوی دلیل: `امکان … وجود ندارد؛ زیرا … .`
- گیومه فارسی `«…»` برای نام سند، سازمان، کد پیگیری و مقدار کوتاه. برای label دکمه گیومه نگذارید.
- دونقطه برای برچسب و مقدار: `کد پیگیری: «ABC123»`.
- سه‌نقطه در حالت در حال انجام، نویسه واحد `…` است: `در حال ذخیره…`؛ سه نقطه ASCII ممنوع.
- عنوان، label، placeholder و دکمه نقطه پایانی ندارند.
- از slash برای دو مفهوم فارسی در متن کاربر استفاده نشود؛ جمله را بازنویسی کنید.
- شناسه و عبارت فنی انگلیسی داخل جمله با جهت مستقل نمایش داده می‌شود؛ پرانتز انگلیسی بخشی از ترجمه اصلی نیست.

## 5. ارقام، تاریخ، زمان و مبلغ

### 5.1 سیاست رقم

| محتوا | نمایش | وضعیت |
| --- | --- | --- |
| شمارش‌ها، شماره صفحه و تعداد | ارقام فارسی طبق تنظیم کاربر؛ تا زمان وجود تنظیم، فرمتر مرکزی فعلی ممکن است لاتین نشان دهد | سیاست هدف `FUTURE PRODUCT DECISION` برای preference؛ فرمت مرکزی `CURRENT` |
| مبلغ و مقدار | رقم طبق تنظیم کاربر، اما دقیقاً با همان دقت اعشاری دریافتی | حفظ decimal string `CURRENT`؛ انتخاب رقم `FUTURE PRODUCT DECISION` |
| کد حساب | رقم/نویسه canonical بدون تبدیل معنایی؛ ترجیحاً لاتین و `dir=ltr` برای کپی دقیق | قرارداد بکند `SUPPORTED` |
| شماره سند | مقدار canonical، بدون ترجمه یا بازسازی؛ `dir=ltr` | `SUPPORTED` |
| ID، ULID، operation key و کد پیگیری | لاتین، `dir=ltr`، فونت مناسب کد، قابل انتخاب/کپی | `SUPPORTED` |
| نام کاربری | عین مقدار ثبت‌شده؛ تبدیل رقم/حروف ممنوع | `CURRENT` |

تبدیل نمایشی رقم نباید مقدار کپی‌شده یا ارسال‌شده را تغییر دهد. گروه‌بندی نمایشی مجاز است؛ parse به `number` برای مبلغ و مقدار مالی ممنوع است.

### 5.2 تاریخ و تقویم

- مقدار قراردادی API برای date-only، `YYYY-MM-DD` است و اکنون عیناً با ارقام لاتین و `dir=ltr` نمایش/ورود می‌شود (`CURRENT`).
- تبدیل به هجری شمسی و انتخاب DatePicker شمسی هنوز `FUTURE PRODUCT DECISION` (OQ-01/OQ-02) است. تا تصمیم، هیچ برچسبی نباید تاریخ میلادی را «شمسی» بنامد.
- پس از تصویب تقویم نمایشی، مقدار ارسالی به API همچنان ISO می‌ماند؛ تبدیل فقط در formatter/parser مرکزی انجام می‌شود.
- بازه تاریخ: `از تاریخ` و `تا تاریخ`. پیام وابسته: `تاریخ پایان نمی‌تواند قبل از تاریخ شروع باشد.`
- تاریخ نامعتبر: `تاریخ سند معتبر نیست. تاریخ را با قالب YYYY-MM-DD وارد کنید.` عبارت قالب با `dir=ltr` خوانده شود.

### 5.3 زمان

- زمان API با formatter مرکزی به شکل بدون ابهام `YYYY-MM-DD HH:mm` نمایش داده می‌شود (`CURRENT`).
- منطقه زمانی باید از قرارداد/تنظیم deployment بیاید؛ نمایش نام منطقه زمانی یا تبدیل محلی بدون قرارداد `CONTRACT GAP` است.
- «تاریخ سند» (محور مالی) با «زمان ثبت» (محور ممیزی) یکی نیست.

### 5.4 مبلغ، اعشار و مقدار منفی

- مقادیر مالی رشته decimal هستند؛ تمام رقم‌های اعشاری بکند، از جمله صفرهای انتهایی، حفظ می‌شوند.
- جداکننده هزارگان فقط تغییر نمایشی است. گرد کردن، جمع زدن یا محاسبه مانده در فرانت‌اند ممنوع.
- علامت منفی پیش از عدد و در محدوده LTR می‌آید: `-1,250.00`. پرانتز حسابداری یا حذف علامت بدون تصمیم محصول ممنوع.
- رنگ قرمز می‌تواند نشانه کمکی مبلغ منفی باشد، اما علامت منفی باید باقی بماند.
- مقدار پولی همیشه واحد روشن دارد؛ مانند `جمع (ریال)`. واحد نباید به خود رشته decimal چسبانده شود.
- تنظیم واحد پایه ریال/تومان در تصمیم مالک پیش‌بینی شده، اما UI فعلی ریال را ثابت نشان می‌دهد. انتخاب/تبدیل واحد `FUTURE PRODUCT DECISION` است و تبدیل تومان صرفاً نمایش خواهد بود، نه محاسبه حقیقت مالی.
- مقدار موجودی `numeric(18,4)` نیز رشته دقیق باقی می‌ماند؛ واحد کالا جدا نمایش داده می‌شود.

## 6. شناسه‌های فنی و جلوگیری از نشت زبان فنی

### 6.1 موارد مجاز

فقط وقتی برای انجام کار یا پشتیبانی لازم است نمایش دهید:

- کد حساب و شماره سند؛
- نام کاربری؛
- شناسه کسب‌وکاری که کاربر واقعاً با آن کار می‌کند؛
- کد پیگیری (correlation ID) پس از خطای سرور/پشتیبانی؛
- قالب ورودی قراردادی مانند `YYYY-MM-DD` در hint.

همه با `dir=ltr`، ترتیب خواندن مستقل، قابلیت انتخاب و بدون تبدیل رقم. label فارسی باقی می‌ماند.

### 6.2 موارد ممنوع در متن اصلی

endpoint، controller، Axios، Prisma، SQL، stack trace، نام exception، HTTP status، enum خام (`final`, `temporary`, `account_not_postable`)، نام فیلد (`financialAreaId`) و کد RBAC نباید پیام اصلی باشند. کد مجوز فقط در جزئیات پشتیبانی قابل‌گسترش است؛ نه دلیل اصلی برای کاربر.

## 7. الگوهای ساخت پیام

### 7.1 موفقیت

**الگو:** `[موجودیت/عمل] با موفقیت [نتیجه].`
اگر فعل به‌تنهایی روشن است، «با موفقیت» حذف می‌شود تا متن طبیعی‌تر باشد.

- `سند با موفقیت ذخیره شد.`
- `سند قطعی شد.`
- `سند معکوس ایجاد شد.`
- `سازمان تغییر کرد.`

موفقیت فقط پس از پاسخ موفق بکند اعلام می‌شود. mutation خوش‌بینانه برای عملیات مالی ممنوع است.

### 7.2 اعتبارسنجی

**الگو:** `[برچسب فارسی فیلد] [نیازمندی/محدوده].`

- `تاریخ سند الزامی است.`
- `مبلغ بدهکار باید بزرگ‌تر از صفر باشد.`
- `تاریخ پایان نمی‌تواند قبل از تاریخ شروع باشد.`

نام فنی فیلد جایگزین label نمی‌شود. پیام بدون سرزنش و بدون `لطفاً` تکراری زیر هر فیلد است.

### 7.3 قاعده کسب‌وکار

**الگو:** `امکان [عمل] وجود ندارد؛ زیرا [دلیل قابل فهم و قطعی]. [اقدام ممکن].`

- `امکان نهایی‌سازی سند وجود ندارد؛ زیرا دوره مالی بسته است. دوره باز دیگری را انتخاب کنید یا با مسئول حسابداری تماس بگیرید.`
- `امکان ثبت ردیف وجود ندارد؛ زیرا حساب انتخاب‌شده قابل ثبت نیست. یک حساب قابل ثبت انتخاب کنید.`

اگر API دلیل قابل اعتماد نمی‌دهد، دلیل حدس زده نمی‌شود؛ پیام عمومیِ همان عمل و کد پیگیری نمایش داده می‌شود و وضعیت `CONTRACT GAP` ثبت می‌گردد.

### 7.4 مجوز

- route: `شما مجوز مشاهده این بخش را ندارید.`
- action: `شما مجوز نهایی‌سازی سند را ندارید.`
- اقدام: `برای دریافت دسترسی با مدیر سامانه تماس بگیرید.` فقط وقتی فرایند سازمانی واقعاً همین است؛ در غیر این صورت CTA بازگشت ارائه شود.

### 7.5 شبکه و سرور

- شبکه: `ارتباط با سرور برقرار نشد. اتصال شبکه را بررسی کرده و دوباره تلاش کنید.`
- سرور بدون کد: `ذخیره سند انجام نشد. لطفاً دوباره تلاش کنید.`
- سرور با کد: `ذخیره سند انجام نشد. در صورت ادامه مشکل، کد پیگیری «ABC123» را به پشتیبانی اعلام کنید.`

کد پیگیری علت خطا نیست و نباید در title باشد.

### 7.6 در حال انجام و خالی

- loading: `در حال دریافت گزارش…`
- empty-after-query: `برای فیلترهای انتخاب‌شده نتیجه‌ای یافت نشد. فیلترها را تغییر دهید.`
- first-use empty: `هنوز سندی ثبت نشده است.` CTA ایجاد فقط اگر capability و مجوز موجود باشد.

## 9. حسابداری: قواعد معنایی حساس

1. `پیش‌نویس` فاز است؛ `موقت` و `قطعی` وضعیت سند هستند. UI نباید هر سند غیرقطعی را پیش‌نویس بنامد.
2. `ذخیره` یا `ثبت` به معنی نهایی‌سازی نیست. پیام ذخیره نباید `سند ثبت قطعی شد` بگوید.
3. نهایی‌سازی، سند را وارد دفاتر و غیرقابل‌ویرایش مستقیم می‌کند؛ معکوس کردن، سند جدید می‌سازد و سند اصلی را حذف نمی‌کند.
4. حذف فقط برای سند پیش‌نویس/موقت مطابق قرارداد مجاز است؛ متن حذف سند قطعی ممنوع است.
5. «مانده» حسابداری با «موجودی» انبار جایگزین نمی‌شود.
6. «حوزه مالی»، «سازمان» و «شعبه» سه مفهوم مستقل‌اند.
7. «حساب قابل ثبت» از داده `isPostable` می‌آید؛ نام سطح حساب به‌تنهایی مجوز ثبت را تعیین نمی‌کند.
8. واحد و دقت مالی از قرارداد می‌آید؛ UI نه دقت جدید می‌سازد و نه جمع گزارش را محاسبه می‌کند.

## 10. مغایرت‌ها و رابطه با FE-UX-01

این موارد **تصریح/اصلاح FE-UX-02** هستند؛ اسناد FE-UX-01 بازنویسی نشده‌اند:

1. FE-UX-01 در چند نمونه، کد مجوز (`Accounting.…`) را متن اصلی alert معرفی می‌کند. از این پس پیام اصلی فارسیِ عمل است؛ کد مجوز فقط جزئیات پشتیبانی است. این تغییر با ممنوعیت شناسه فنی در UX سازگار است.
2. نمونه تأیید FE-UX-01 (`آیا مطمئنید؟`) از این پس نامعتبر است؛ dialog باید پیامد را توضیح دهد و دکمه عمل‌محور داشته باشد.
3. FE-UX-01 عبارت `سند معکوس (Reversal)` و متن فعلی داشبورد را دارد. واژه رسمی فقط `سند معکوس` است.
4. FE-UX-01 تاریخ `YYYY-MM-DD` را قرارداد قطعی نمایش می‌داند و هم‌زمان DatePicker شمسی را آینده می‌نامد. FE-UX-02 روشن می‌کند: ISO وضعیت فعلی است؛ نمایش شمسی تصمیم آینده و صرفاً لایه نمایش است.
5. dictionary فعلی `انصراف`، `جستجو` و `سیل‌شده` دارد. واژه‌های رسمی FE-UX-02 به‌ترتیب `لغو`، `جست‌وجو` و `مهروموم‌شده` هستند؛ اصلاح production در این تسک انجام نشده است.
6. `docs/frontend/standards.md` تنظیم رقم و واحد را پیش‌بینی می‌کند، اما تنظیم کاربر هنوز وجود ندارد. این سند آن را `FUTURE PRODUCT DECISION` می‌داند و رفتار فعلی را صادقانه ثبت می‌کند.
