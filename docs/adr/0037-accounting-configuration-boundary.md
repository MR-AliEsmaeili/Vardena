## Context

The Owner confirmed the hybrid model the repository already decided in *mechanism* — Vardena owns accounting/control semantics, the organization owns its account structure — and added two things the repository does **not** have: a Vardena-shipped **standard/base Accounting structure** (Q2) and **Vardena-standardized Control Roles**, mandatory only where active Accounting operations require them (Q4). The *mechanism* is implemented and version-pinned (§1); the *content* is not (boundary below). Contract §1.2 non-goal 1 refused to define a chart template, so Q2 is a new commitment (D-5) whose *content* stays expert-gated.

## Decision

1. **Configurable, bounded level count (Q1).** The number of accounting code levels is **never hardcoded to four**; `گروه / کل / معین / تفصیلی` is level *vocabulary*, not four tables or a constant (§8.1/AC-D-06). An organization configures level count, titles, digit lengths, `level_kind` labels and per-level posting defaults inside a **controlled Vardena-supported structure**: code-defined caps (`max_depth ≤ 8`, total code length ≤ 32) plus the version/pinning rules of ADR-0028 and contract §9.4. Configurable ≠ unlimited arbitrary hierarchy — raising a cap is a code change with an ADR note, not customer configuration (§9.1).
2. **Hybrid model (Q2).** Vardena defines accounting/control **semantics** (invariants, control roles, level mechanics, the shape of posting rules, reporting sources); the organization owns its **account structure** (levels, titles, digit lengths, accounts, role mappings) as versioned configuration data within that supported model.
3. **A Vardena base Accounting structure exists and is configurable (Q2).** Vardena provides a standard/base structure an organization adopts and then configures. It must ship as **versioned configuration data or a template artifact** — never as per-customer code branches, never as hardcoded account rows in domain logic, never as a seed that silently creates accounts in an existing organization. Its **content** (codes, Persian titles, level shape, role mappings) remains EXPERT-GATED under **OQ-25** and is *not* decided here (baseline D-5: none of it exists today).
4. **Control Roles are Vardena-standardized (Q4, confirming AC-D-09).** The role vocabulary is code-defined (adding a role is a code change — the ADR-0023 §2 pattern); organizations map **their own accounts** to those roles once, as effective-dated, permission-gated, audited configuration; posting rules and statutory profiles reference **roles, never free customer codes**.
5. **Mandatory-ness is demand-driven (Q4).** Only roles required by **active** Accounting operations are mandatory: a role becomes required when a shipped operation consumes it (a posting rule, a year-transition document, a control report), not because a fixed list says so. Which roles those are, and the role list itself, stay EXPERT-GATED under OQ-25 until the consuming operation is authorized — no role is invented here (AR-31/AG-09).
6. **Detail accounts: both kinds (Q6, confirming AC-D-15/§11.2).** Tree-based detail accounts (the deepest configured level of the tree) **and** floating detail items (`تفصیلی شناور` — outside the tree, one identity, no nature of its own, combinable with any compatible account) are both supported; which an organization uses, and where, is configuration — not a product fork, not an either/or default.
7. **Dimensions: configurable, typed, capped (Q7, confirming AC-D-11…AC-D-14).** A general dimension model (cost center, project, branch, counterparty, …) with a configured count under a code-defined cap, typed item tables, optional logical master-data binding, and a per-(account, dimension) `requirement` ∈ `required | optional | forbidden` validated on the line (AC-I-18). **Never** a giant EAV structure and **never** a giant JSONB blob for ledger dimensions (`configurability-architecture.md` §5.2, contract §10.6, AR-29). Per-dimension defaults, count and binding rules remain **OQ-41**.
8. **Configurability principle (Q17, Decision D).** The Accounting Core stays standardized, safe and integrity-preserving while a Configuration Layer provides high flexibility; configuration may **not** violate the domain invariants (contract §25, AC-I-01…AC-I-22), authorization (ADR-0016, AR-21/AR-22, no wildcard — OQ-21), auditability (contract §23, AR-23), tenant isolation (ADR-0021/0025, AC-I-01/16) or data integrity (AR-13, AC-I-05/06/07/11/15). A configuration that would violate one is **refused by validation**, not merely discouraged by convention. *High configurability does not mean unrestricted configurability*: where the supported vocabulary cannot express a need, that is a product gap to design (`configurability-architecture.md` §2), never a hole to open — no free-form scripts, expressions, user SQL or per-customer logic in configuration.

## Current implementation boundary / non-goals

The *mechanism* above already exists and is unchanged (configurable levels/digit lengths/postability defaults, versioning + pinning, single ACTIVE, operational freeze); everything that is *content or new capability* — base structure, control roles and their mappings, dimensions, floating details — remains an unimplemented candidate in [`task-index.md`](../accounting/task-index.md) §4, each needing its own task per §7. **This ADR implements and authorizes none of them, and it is not an implementation design for the configuration subsystem**: base-structure content and control-role policy stay subject to OQ-25 (dimensions to OQ-41) and to future expert-gated decisions. No speculative column may be added before a consuming operation exists (AR-29) — why `control_role` and `reserved_ranges` are still absent from the schema.

## Consequences

- OQ-25 (role list, mandatory roles, base-structure content, per-level posting policy, deactivation guards, statutory layouts), OQ-41 (dimension count/defaults/binding) and OQ-22/OQ-55 (branch/department as dimensions) all stay **OPEN**.
- A future base-structure delivery must be reviewable as data: versioned, documented, Persian-titled, mapped to control roles, adoptable without editing an existing chart (ADR-0035 governs any later re-coding).
- Control roles and dimensions widen the *configuration* surface, not the ledger; ADR-0034 governs the posting semantics configuration may express.
- Risk recorded: a request for custom level semantics, an invariant switch or a formula field on accounts is refused by §8 and answered with a product-gap analysis, not a configuration extension.
