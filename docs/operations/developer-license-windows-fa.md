# راهنمای کامل و سادهٔ مجوز توسعه‌دهندهٔ Vardena در ویندوز

این راهنما از صفر تا نتیجه است و برای کسی نوشته شده که برنامه‌نویس نیست. مجوز رسمی توسعه‌دهنده (`DEVELOPER`) بدون اجرای Owner Licensing و بدون ساخت مشتری تجاری صادر می‌شود، اما همچنان امضای Ed25519، تاریخ، سقف‌ها، دسترسی‌ها و شناسهٔ نصب را بررسی می‌کند.

> **مرز امنیتی مهم:** `NODE_ENV=development` و `LICENSE_PROVIDER=local-development` مجوز رسمی نیستند. مجوز توسعه‌دهنده فقط وقتی پذیرفته می‌شود که مدیر استقرار، سیاست و کلید عمومی مخصوص آن را صریحاً فعال کرده باشد.

## نتیجه‌ای که در پایان می‌گیرید

- یک کلید خصوصی که فقط روی رایانهٔ امن صادرکننده می‌ماند؛
- یک کلید عمومی که روی نصب‌های مجاز قرار می‌گیرد؛
- یک فایل مثل `vardena-developer-license.vdev.json` که فقط برای **یک** `installationId` معتبر است؛
- وضعیت برنامه با `licenseType=DEVELOPER`، بدون `customerId` و بدون مشتری ساختگی.

## پیش‌نیازها

1. ویندوز 10/11 یا Windows Server با Windows PowerShell 5.1؛
2. Node.js نسخهٔ 22.12 یا جدیدتر و npm؛
3. یک نسخهٔ محلی از مخزن Vardena؛
4. دسترسی مدیر استقرار برای تنظیم متغیرهای محیطی API و Worker؛
5. حساب Vardena دارای مجوز `Licensing.License.Activate` برای واردکردن فایل؛
6. یک پوشهٔ پشتیبان رمزگذاری‌شده مطابق سیاست سازمان.

کلید خصوصی، فایل واقعی مجوز و رمزها را در Git، GitHub، چت، تیکت، ایمیل عمومی، `.env` داخل مخزن، پایگاه داده یا Frontend قرار ندهید.

## روش پیشنهادی: پنجرهٔ Workbench

### ۱) بازکردن PowerShell

روی Start کلیک کنید، `Windows PowerShell` را جست‌وجو و اجرا کنید. سپس به پوشهٔ مخزن بروید؛ مسیر زیر را با مسیر واقعی خودتان جایگزین کنید:

```powershell
Set-Location "C:\Work\Vardena"
```

یک بار وابستگی‌های هر دو ابزار را نصب کنید. این مرحله ممکن است به شبکه نیاز داشته
باشد؛ پیش از ساخت کلید و صدور، رایانه را مطابق سیاست سازمان آفلاین کنید:

```powershell
Push-Location .\owner-licensing\backend
npm ci --no-audit --no-fund
if ($LASTEXITCODE -ne 0) { throw "نصب وابستگی‌های Owner ناموفق بود." }
Pop-Location
Push-Location .\backend
npm ci --no-audit --no-fund
if ($LASTEXITCODE -ne 0) { throw "نصب وابستگی‌های Backend ناموفق بود." }
Pop-Location
```

برای همین پنجره اجازهٔ اجرای اسکریپت بدهید و Workbench را باز کنید:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\tools\licensing-workbench\Start-VardenaLicensingWorkbench.ps1
```

این تغییر فقط تا بسته‌شدن همان PowerShell معتبر است. اگر سیاست سازمان اجرای اسکریپت را ممنوع کرده، آن را دور نزنید و از مدیر سیستم کمک بگیرید.

### ۲) ساخت ابزارها

در پنجرهٔ Workbench روی **«ساخت ابزار امضا»** کلیک کنید. این دکمه هم ابزار امضای Owner و هم ابزار مجوز توسعه‌دهنده را می‌سازد. موفقیت باید صریحاً نمایش داده شود.

### ۳) ساخت کلید مخصوص توسعه‌دهنده

1. در بخش **«مجوز رسمی توسعه‌دهنده»** یک پوشهٔ پایه مثل `C:\Vardena-Keys` انتخاب کنید.
2. روی **«ساخت کلید توسعه‌دهنده»** کلیک کنید.
3. برنامه یک زیرپوشهٔ تاریخ‌دار می‌سازد، ارث‌بری دسترسی Windows را حذف و فقط کاربر فعلی را مجاز می‌کند.
4. سه فایل ساخته می‌شود:
   - `developer-license-key.pkcs8` — **خصوصی و محرمانه**؛
   - `developer-license-public-key.txt` — عمومی؛
   - `developer-license-key-info.json` — شناسه و مقدار عمومی `trustEntry`.
5. از فایل خصوصی پشتیبان رمزگذاری‌شده بگیرید. محتوای آن را هرگز کپی یا نمایش ندهید.

اگر فایل‌ها از قبل وجود داشته باشند، ابزار آن‌ها را بازنویسی نمی‌کند. این خطا را با حذف کورکورانهٔ فایل قبلی حل نکنید؛ پوشهٔ تازه بسازید.

### ۴) گرفتن شناسهٔ نصب مقصد

در برنامهٔ Vardena مقصد وارد صفحهٔ مجوز شوید و `installationId` را دقیقاً کپی کنید. این شناسه متعلق به Backend است؛ خودتان آن را حدس نزنید و از شناسهٔ نصب دیگری استفاده نکنید.

هر فایل توسعه‌دهنده فقط برای یک نصب است. برای نصب دوم باید فایل مستقل صادر شود.

### ۵) فعال‌کردن اعتماد روی نصب مجاز

فایل `developer-license-key-info.json` را با یک ویرایشگر متنی باز کنید و فقط مقدار عمومی `trustEntry` را بردارید. **فایل خصوصی را به سرور نبرید.**

در تنظیمات محیطی API و Worker مقصد این مقادیر را قرار دهید:

```dotenv
LICENSE_PROVIDER=persistent
DEVELOPER_LICENSES_ENABLED=true
DEVELOPER_LICENSE_SIGNING_PUBLIC_KEYS=KEY_ID:BASE64_PUBLIC_KEY
```

`KEY_ID:BASE64_PUBLIC_KEY` را با مقدار کامل `trustEntry` جایگزین کنید. سپس API و Worker را با روش رسمی استقرار خود راه‌اندازی مجدد کنید و سالم‌بودن هر دو را بررسی کنید.

برای نصب مشتری که نباید مجوز توسعه‌دهنده بپذیرد، تنظیم درست این است:

```dotenv
DEVELOPER_LICENSES_ENABLED=false
DEVELOPER_LICENSE_SIGNING_PUBLIC_KEYS=
```

تغییر `NODE_ENV` هرگز جایگزین این تصمیم نیست. کلید عمومی توسعه‌دهنده را در `LICENSE_SIGNING_PUBLIC_KEYS` تجاری قرار ندهید.

### ۶) صدور فایل

در Workbench روی **«صدور مجوز توسعه‌دهنده»** کلیک کنید و به‌ترتیب وارد کنید:

- همان `installationId` مقصد؛
- شناسهٔ پایدار غیرتجاری مثل `developer-ali`؛
- نام نمایشی؛
- پایان اعتبار UTC؛
- زمان شروع اعتبار UTC (برای جایگزینی، مقدار پیش‌فرض ۱۵ دقیقه آینده است تا فرصت انتقال و Import داشته باشید)؛
- سقف مثبت سازمان‌ها؛
- سقف مثبت کاربران؛
- ماژول‌ها با ویرگول، مثل `organization,users,rbac`؛
- قابلیت‌های اختیاری؛
- برای اولین صدور، جایگزینی را خالی بگذارید.

مسیر خروجی جدیدی انتخاب کنید. اگر فایل قبلاً وجود دارد، نام تازه بدهید. ابزار ورودی را بررسی می‌کند، امضا می‌کند، با کلید عمومی خودش دوباره صحت را می‌سنجد و فقط بعد فایل را می‌نویسد. محتوی کلید خصوصی یا خود فایل مجوز در گزارش چاپ نمی‌شود.

مجوز VDEV1 همیشگی یا نامحدود نیست. تاریخ پایان، سقف سازمان و سقف کاربر الزامی و محدود هستند. ثبت Device در VDEV1 پشتیبانی نمی‌شود و سقف Device صفر است؛ برای دورزدن آن مشتری ساختگی نسازید. سند ابطال فعلی VREV1 نیز مخصوص مشتری تجاری است و VDEV1 در نسخهٔ ۱ سند ابطال جداگانه ندارد؛ در رخداد امنیتی از سیاست/اعتماد استقرار و جایگزینی کنترل‌شده استفاده کنید.

### ۷) انتقال و فعال‌سازی

1. فقط فایل `.vdev.json` را با روش انتقال مورد تأیید سازمان به نصب مقصد ببرید.
2. با حساب دارای `Licensing.License.Activate` وارد Vardena شوید.
3. همان مسیر رسمی فعال‌سازی/Import مجوز را باز کنید.
4. فایل را انتخاب و فعال کنید.
5. نتیجه را بررسی کنید:
   - `licenseType` برابر `DEVELOPER`؛
   - `developerId` و نام درست؛
   - `customerId` و `customerCode` خالی؛
   - `installationId`، تاریخ پایان، سقف‌ها و ماژول‌ها درست؛
   - وضعیت فعال.

Frontend مرجع تصمیم نیست؛ Backend تمام سقف‌ها، ماژول‌ها، RBAC و دسترسی داده را اعمال می‌کند.

### ۸) تمدید یا جایگزینی

برای جایگزینی، `operationId` نسخهٔ قبلی را از وضعیت مجوز بردارید. در Workbench آن را در سؤال «جایگزینی» وارد و فایل تازه‌ای با تاریخ‌ها و سقف‌های روشن صادر کنید. شناسهٔ عملیات قبلی را به‌عنوان عملیات جدید تکرار نکنید. `developerId` باید همان دارندهٔ قبلی بماند؛ VDEV1 مسیر انتقال بی‌صدای دارنده ندارد و تغییر آن رد می‌شود.

کاهش سقف یا حذف ماژولی که اکنون مصرف می‌شود ممکن است مطابق قواعد موجود رد شود. تاریخ را به گذشته برنگردانید و سابقهٔ پایگاه داده را حذف نکنید.

## روش خط فرمان (برای مدیر فنی)

این فرمان‌ها از ریشهٔ مخزن و با PowerShell نوشته شده‌اند.

### نصب و ساخت

```powershell
Set-Location "C:\Work\Vardena\backend"
npm ci --no-audit --no-fund
npm run build:tools
```

### ساخت پوشهٔ امن و کلید

```powershell
$KeyDir = "C:\Vardena-Developer-Authority"
New-Item -ItemType Directory -Path $KeyDir | Out-Null
$Sid = [System.Security.Principal.WindowsIdentity]::GetCurrent().User.Value
icacls.exe $KeyDir /inheritance:r /grant:r "*$Sid`:(OI)(CI)(F)"
npm run developer-license:keygen -- --out-dir $KeyDir
```

اگر پوشه یا فایل‌های کلید قبلاً وجود دارند، برای جلوگیری از بازنویسی از یک پوشهٔ تازه استفاده کنید. بررسی ACL نباید دور زده شود.

### صدور نمونهٔ کامل

تاریخ‌ها و شناسه‌ها را با مقدار واقعی جایگزین کنید. قالب زمان باید دقیقاً UTC باشد:

```powershell
npm run developer-license:issue -- `
  --private-key-file "C:\Vardena-Developer-Authority\developer-license-key.pkcs8" `
  --out "C:\Vardena-Transfer\vardena-developer-license.vdev.json" `
  --installation "01JDEVINSTALLATION000000000" `
  --developer-id "developer-ali" `
  --developer-name "Ali Example" `
  --operation-id "dev-operation-2026-001" `
  --license-id "dev-license-2026-001" `
  --issued-at "2026-10-25T10:00:00.000Z" `
  --valid-from "2026-10-25T10:00:00.000Z" `
  --valid-until "2027-01-25T10:00:00.000Z" `
  --organizations 2 `
  --users 10 `
  --modules "organization,users,rbac" `
  --features "developer-tools"
```

وقتی تمام ورودی‌ها و کلید یکی باشند، Ed25519 و قالب canonical همان فایل را تولید می‌کنند. برای عملیات واقعی جدید شناسهٔ عملیات تازه استفاده کنید؛ تکرار فایل قبلی در مقصد به‌عنوان Replay رد می‌شود.

## خطاهای رایج

- **`developer-license-disabled`**: نصب اجازهٔ پذیرش ندارد. `NODE_ENV` را تغییر ندهید؛ تأیید و تنظیم صریح لازم است.
- **`unknown-key` یا خطای امضا**: `trustEntry` عمومی اشتباه/ناقص است یا فایل تغییر کرده. کلید خصوصی را به سرور منتقل نکنید.
- **`installation-mismatch`**: فایل برای نصب دیگری است. فایل مستقل صادر کنید؛ امضا را ویرایش نکنید.
- **منقضی/غیرفعال/زمان آینده**: ساعت UTC و تاریخ‌ها را بررسی و با operation جدید دوباره صادر کنید.
- **`duplicate-operation`**: عملیات قبلاً ثبت شده؛ سابقه را پاک نکنید.
- **`license-type-conflict`**: نصب مشتری تجاری یا سابقهٔ نوع دیگری دارد، یا مسیر ویژهٔ تجاری استفاده شده. مشتری ساختگی نسازید؛ نصب توسعه‌دهندهٔ مجاز یا مسیر تجاری درست را انتخاب کنید.
- **خطای دسترسی کلید**: ACL پوشه/فایل گسترده است. فقط دسترسی کاربر صادرکننده، SYSTEM و Administrators قابل قبول است.
- **خطای overwrite**: مسیر خروجی تازه انتخاب کنید؛ ابزار عمداً فایل را جایگزین نمی‌کند.
- **Device**: در نسخهٔ VDEV1 عمداً پشتیبانی نمی‌شود.

## اگر کلید خصوصی گم یا افشا شد

1. صدور را فوراً متوقف کنید.
2. روی نصب‌های مجاز، طبق فرایند تغییر کنترل‌شده `DEVELOPER_LICENSES_ENABLED=false` کنید یا کلید عمومی افشاشده را از اعتماد بردارید؛ API و Worker را هماهنگ به‌روزرسانی کنید.
3. شواهد و فایل‌های قبلی را حذف نکنید.
4. در یک پوشهٔ امن کلید تازه بسازید.
5. ابتدا کلید عمومی تازه را روی نصب‌های تأییدشده منتشر و سلامت را بررسی کنید.
6. برای هر نصب فایل مستقل تازه صادر کنید.

چون سیستم آفلاین است، سرویس مرکزی برای ابطال فوری وجود ندارد. برنامه‌ریزی انتشار اعتماد عمومی بخشی از عملیات امنیتی است.

- [ ] API و Worker سیاست و کلید عمومی یکسان دارند.
- [ ] نصب‌های مشتری غیرمجاز `DEVELOPER_LICENSES_ENABLED=false` دارند.
- [ ] فایل برای `installationId` دقیق مقصد است.
- [ ] تاریخ پایان و سقف‌ها محدود و روشن‌اند.
- [ ] فایل از مسیر رسمی Import و با RBAC وارد شده است.
- [ ] وضعیت `DEVELOPER` و نبود customer تأیید شده است.
