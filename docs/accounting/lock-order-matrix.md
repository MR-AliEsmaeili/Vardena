# Accounting Module — Lock-Order Matrix (AR-11)

**Scope:** every transaction that holds `SELECT … FOR UPDATE / FOR SHARE` row locks in `accounting.*` (`backend/src/modules/accounting/data/accounting-locks.ts` + `backend/src/modules/accounting/data/accounting-documents.repository.ts`). The order is **total and never reversed** — no transaction ever waits on a row whose lock it has not already taken in the order below, so no deadlock cycle exists. Prisma cannot express `FOR` locks, hence the parameterized raw SQL documented in `docs/modules.md §Accounting (AR-11)`.

**Notation:** `→` means "then, in the same transaction, while still holding prior locks". `ASC id` means multiple rows of that kind are locked ascending by id (deterministic, avoids `id-ordered deadlock`). `FOR SHARE` conflicts with `FOR UPDATE`; `FOR UPDATE` is exclusive.

---

## 1. Global Order

```
financial_area (FOR UPDATE)
  → fiscal_year (FOR UPDATE)
    → accounting_period (FOR UPDATE)
      → coding_structure_version / accounting_configuration (FOR UPDATE)
          ← the ONLY place a voucher write touches a configuration row: the
            Task-13 usage marker inside `finalizeChecked` (row D4″ below)
        → account (FOR UPDATE for chart writes, FOR SHARE for voucher writes, ASC id)
          → account_balance_projections (FOR UPDATE, ordered by composite projection key, Task 12)
            → accounting_document (FOR UPDATE, last)
```

- Calendar writes never hold an account lock before taking the year/period locks.
- Account writes lock the relevant `coding_structure_version` / `accounting_configuration` before accounts.
- Voucher writes take `financial_area → fiscal_year → accounting_period` (via `lockScopeInTx`), then (Task 13) the **usage marker** on the `accounting_configuration` rows the voucher's lines actually pinned, then `account(s) FOR SHARE ASC`, then (Task 12) `account_balance_projections FOR UPDATE` by projection key, then `accounting_document FOR UPDATE` **last** — so no calendar/account write ever waits on a document row.
- The marker is why a finalize is **not** a pure configuration reader: it holds row-exclusive locks on the touched configuration ids while it writes `operationally_used_at`, and it releases them at `COMMIT`. Chart writes (`AC11-2`, `A1`, `A5`) lock the same table at the same position, so the two families serialize instead of cycling — inverting the order (account before configuration) deadlocks, demonstrated by `backend/prisma/rehearsal/task-13-operational-freeze/rehearse.mjs` §7 on a real server.
- Multi-row locks of one kind are always `ASC id`; transaction inputs are deduplicated + sorted before locking.
- No path waits on `ledger_entries` — ledger rows are `INSERT`-only and are never locked. The `UNIQUE (voucher_line_id)` on `ledger_entries` and `UNIQUE (org, area, year, period, account)` on `account_balance_projections` are the cross-transaction backstops (first-persister-wins).

### Task 14 — Dedicated Rows (period-lifecycle enforcement, §15.5 / §7.2)

Task 14 adds **no lock**: the gate it hardens reads the period/year rows that
row `D4″` already locks. What it fixes is _where_ the locked status is judged
(row `D4‴` above) and _which_ organization the locked rows must belong to
(rows P1/P2). The four races below are the ones the kernel test suite
(`backend/test/accounting-period-lifecycle-live.e2e-spec.ts`, real PostgreSQL,
independent connections) executes; the "winner" column states what the
implementation must produce.

| #         | Race (two transactions, independent connections)                                                 | Interleaving                                                                                                                 | Mode                                     | Required outcome                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **T14-1** | `finalizeChecked` (voucher dated in period P) vs `AccountingPeriodsService.transition(P, close)` | Finalize holds `area → year → period(P)` and has not committed; `close` waits on the period row (its first conflicting lock) | UPDATE (finalize) / UPDATE (close waits) | Finalize sees `open` (committed), writes `state=final` + ledger rows + operation row and commits **first**; `close` then locks the period, reads the committed `open` status and applies `open→closed`. **Both succeed**: the voucher was dated into a period that was open at commit time. Result: period `closed`, document `final`, N ledger rows, 1 operation row, `AccountingPeriod.Closed` published once.                                       |
| **T14-2** | same pair, opposite order                                                                        | `close` commits first; finalize then locks the period and finds `closed`                                                     | UPDATE / UPDATE                          | Finalize is refused with `AccountingDocumentScopeRejectedError` `{scope:'period', status:'closed'}` **before** the freeze marker, before any `FOR SHARE`/`FOR UPDATE` beyond the scope locks, before any write. Zero trace: no ledger entry, no `state=final`, no operation row, `operationally_used_at` still `NULL`, no projection change. This is the "no posting after close" guarantee (AC-I-04, §7.2 rule 4) — it is serialization, not a retry. |
| **T14-3** | two concurrent `close` operations on the same period                                             | one commits; the other waits on the year→period locks                                                                        | UPDATE / UPDATE (waits)                  | Exactly one transition applies; the loser re-reads the **locked** row, `planAccountingPeriodTransition` refuses `closed→closed` and it answers `PeriodTransitionConflictError` (409 — the period moved) with no second event and no status write. One `AccountingPeriod.Closed` per committed move.                                                                                                                                                    |
| **T14-4** | period create/transition/close called with a **foreign** organization id                         | caller's `organizationId` reaches the repository with a row id belonging to another org                                      | (no new lock)                            | The repository compares the caller's organization against the **locked** year and period rows inside the transaction and refuses (`Error`, a boundary violation — the service's in-scope resolution answers 404 first for a foreign id, `AC-I-16`). No cross-organization lifecycle write is possible even if a future caller skips that resolution.                                                                                                   |

> **Gate placement is the observable part.** T14-2 additionally proves _where_
> the refusal happens by holding the row Task 14 could have waited on: with an
> `accounting_configuration` row held `FOR UPDATE` by an unrelated transaction,
> a posting into a `closed` period must still be refused **promptly** (it never
> queues on the freeze marker, the account locks or the projections), while an
> implementation that judged the status after those steps would block until the
> holder released. The test asserts the refusal (with `{scope:'period',
status:'closed'}`) arrives while the configuration row is still locked.

## 3. Cross-Cutting Notes

- **Sort & dedup discipline:** every multi-row lock input is deduplicated (`Set`) + sorted ascending by id before the loop. Callers that pass `accountId`s from voucher lines or projection keys from ledger deltas apply this before the first `SELECT … FOR SHARE/UPDATE` in that transaction — the per-transaction loop then awaits each `SELECT` sequentially (never `Promise.all` across `FOR` queries), so the hold order is deterministic.

- **Idempotency row placement:** `accounting_posting_operations` is always the **last** `INSERT` of any `accounting.*` transaction (`createChecked`, `finalizeChecked`, and the future correction task). A lost `operation_key` race therefore aborts the whole transaction; the loser re-reads via `findByKey` and replays the winner's stored result — never creating a second effect (AC-I-12, §16.4). This placement is unchanged by Task 12's added balance `UPSERT` — the operation row stays LAST even after the new tail.

- **Prisma migration drift risk:** no `CHECK` constraints, no triggers, no partial unique indexes visible to Prisma are introduced for this invariant — Prisma cannot represent them, and the next `prisma migrate dev` would silently `DROP` them (the reason `is_active` / lifecycle rules are domain-enforced and the "exactly one ACTIVE version per org" guarantee is tested in `test/accounting-configuration-live.e2e-spec.ts` + the rehearsal). The Task-12 migration's raw partial index for the one-ACTIVE guarantee is carried deliberately with a test-rehearsed exemption (Task 11 pattern).

- **Operational-usage marker (Task 13):** `accounting_configuration.operationally_used_at` is written by exactly one statement, inside `finalizeChecked` at the configuration position of the global order (row D4″). Two rules hold it in place: (a) it is a _side effect_ of a committed business operation, never an operation of its own — adding a route, a permission or a "mark the ACTIVE configuration" heuristic would let a caller freeze a configuration without doing anything (and reopen the DoS-by-edit vector `ensureConfigurationMutable` exists to close); (b) it must stay _before_ the account locks and _before_ any ledger insert, so it never holds a ledger or balance lock while waiting for a configuration, and it agrees with the chart's configuration-before-account order (`A1`, `A5`). A new writer of that column must update this note and the `D4″` row with it.

- **Lifecycle gate position (Task 14):** `finalizeChecked` judges the **locked** period/year status as its **first** action after the scope locks (row `D4‴`) and re-judges it after the document lock as the stored-scope verdict. The early judgement is what makes the refusal cheap and observable — a `closed`/`sealed` period refuses before the freeze marker, before accounts `FOR SHARE`, before projections `FOR UPDATE` and before any write — while the late one remains the authoritative check that the re-read document still points at an open scope. The status of the _locked_ period row is the single authority for postability; no intermediate cache, no service-level pre-check and no status column elsewhere duplicates it. A change that moves this gate **after** any write, or that re-orders it after the configuration/account/projection locks, must update this note, row `D4‴` and the gate tests (`backend/test/accounting-period-lifecycle-live.e2e-spec.ts`, "refuses a closed period without touching the configuration the posting would mark").

- **Corrected rows (Task 14, documentation only):** rows `Y2`, `Y3`, `P1` and `P2` previously claimed an `financial_area FOR UPDATE` first. Reading the code, those four operations lock the **fiscal year** (and then the period) only — `AccountingPeriodsRepository.createChecked/transitionChecked`, `FiscalYearsRepository.updateChecked/transitionChecked`. That is a _subsequence_ of the global order, which is why the header of `accounting-locks.ts` states the invariant as "no transaction holding a year lock ever waits on an area lock": the order is never reversed, and no cycle exists. Task 14 also added the organization-ownership assertion on the locked rows in those two repositories (rows P1/P2). The other rows are unchanged.

this file is the canonical concurrency reference for Accounting writes. Any new `SELECT … FOR` lock or any change that moves a lock earlier/later must update this matrix **and** the header of `backend/src/modules/accounting/data/accounting-locks.ts` in the same PR, and must keep the "never reversed" order — especially the Tail position of `account_balance_projections` between accounts and the document.
