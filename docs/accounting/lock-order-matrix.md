# Accounting Module — Lock-Order Matrix (AR-11)

**Scope:** every transaction that holds `SELECT … FOR UPDATE / FOR SHARE` row locks in `accounting.*` (`backend/src/modules/accounting/data/accounting-locks.ts` + `backend/src/modules/accounting/data/accounting-documents.repository.ts`). The order is **total and never reversed** — no transaction ever waits on a row whose lock it has not already taken in the order below, so no deadlock cycle exists. Prisma cannot express `FOR` locks, hence the parameterized raw SQL documented in `docs/modules.md §Accounting (AR-11)`.

**Notation:** `→` means "then, in the same transaction, while still holding prior locks". `ASC id` means multiple rows of that kind are locked ascending by id (deterministic, avoids `id-ordered deadlock`). `FOR SHARE` conflicts with `FOR UPDATE`; `FOR UPDATE` is exclusive.

---

## 1. Global Order

```
financial_area (FOR UPDATE)
  → fiscal_year (FOR UPDATE)
    → accounting_period (FOR UPDATE)
      → coding_structure_version / accounting_configuration (FOR UPDATE)
          ← the ONLY place a voucher write touches a configuration row: the
            Task-13 usage marker inside `finalizeChecked` (row D4″ below)
        → account (FOR UPDATE for chart writes, FOR SHARE for voucher writes, ASC id)
          → account_balance_projections (FOR UPDATE, ordered by composite projection key, Task 12)
            → accounting_document (FOR UPDATE, last)
```

- Calendar writes never hold an account lock before taking the year/period locks.
- Account writes lock the relevant `coding_structure_version` / `accounting_configuration` before accounts.
- Voucher writes take `financial_area → fiscal_year → accounting_period` (via `lockScopeInTx`), then (Task 13) the **usage marker** on the `accounting_configuration` rows the voucher's lines actually pinned, then `account(s) FOR SHARE ASC`, then (Task 12) `account_balance_projections FOR UPDATE` by projection key, then `accounting_document FOR UPDATE` **last** — so no calendar/account write ever waits on a document row.
- The marker is why a finalize is **not** a pure configuration reader: it holds row-exclusive locks on the touched configuration ids while it writes `operationally_used_at`, and it releases them at `COMMIT`. Chart writes (`AC11-2`, `A1`, `A5`) lock the same table at the same position, so the two families serialize instead of cycling — inverting the order (account before configuration) deadlocks, demonstrated by `backend/prisma/rehearsal/task-13-operational-freeze/rehearse.mjs` §7 on a real server.
- Multi-row locks of one kind are always `ASC id`; transaction inputs are deduplicated + sorted before locking.
- No path waits on `ledger_entries` — ledger rows are `INSERT`-only and are never locked. The `UNIQUE (voucher_line_id)` on `ledger_entries` and `UNIQUE (org, area, year, period, account)` on `account_balance_projections` are the cross-transaction backstops (first-persister-wins).

### Task 12 — Dedicated Rows (explicitly required, §20 verification gate)

| # | Operation | Lock order | Mode | Invariant |
|---|---|---|---|---|
| **R1** | Finalize voucher that touches 1 existing balance key | `area → year → period FOR UPDATE` → `accounts FOR SHARE ASC` → **`balance FOR UPDATE` (existing row by key, ASC)** → `document FOR UPDATE` → ledger INSERT → **balance UPSERT (+= Δ)** → operation INSERT | UPDATE/SHARE/UPDATE/UPDATE | Row exists → `INSERT+S` hold; delta summed exactly, result `>0` ⇒ row survives with new sums. |
| **R2** | Finalize voucher creating a new balance key | `area → year → period FOR UPDATE` → `accounts FOR SHARE ASC` → **`balance probe (no row ⇒ no wait)`** → `document FOR UPDATE` → ledger INSERT → **balance INSERT (new ULID, turnover=Δ)** → operation INSERT | UPDATE/SHARE/(no wait)/UPDATE | Absent ⇒ no wait; `INSERT` races are serialized by `UNIQUE(org, area, year, period, account)` backstop — loser violates, aborts whole txn (caller retries or replays via operation idempotency). |
| **R3** | Finalize that zeroes a balance key (counter-turnover) | `area → year → period` → `accounts FOR SHARE` → **`balance FOR UPDATE` (row exists)** → `document FOR UPDATE` → ledger INSERT → Σ becomes `0/0` → **balance DELETE** → operation INSERT | UPDATE/SHARE/UPDATE/UPDATE/DELETE | AC-I-19c preservation: `DELETE` restores absence=zero. The key can be re-created later by another voucher — still absence-semantics. |
| **R4** | Two concurrent finalizations, disjoint keys | `area→year→period` lock held by both (same rows, `FOR UPDATE` serializes if one is writing period status, otherwise concurrent) → each holds its own `accounts FOR SHARE` subset (disjoint or overlapping SHARE) → each holds its own **`balance FOR UPDATE` key** (disjoint ⇒ no wait) → each `document FOR UPDATE` (different docs) | UPDATE/SHARE/UPDATE | No wait on balance keys → fully concurrent. Ledger `UNIQUE(voucher_line_id)` stays per-line, so disjoint vouchers never conflict. |
| **R5** | Two concurrent finalizations, same key | … → `accounts FOR SHARE` (overlap = SHARE, not exclusive) → **`balance FOR UPDATE` SAME KEY — second waiter blocks on first's `FOR UPDATE` until first COMMITS** → second re-reads winner's committed turnover + its own Δ | UPDATE/SHARE/**UPDATE (contention)** | Correct: second sees winner's committed sums, `UPSERT` adds its Δ atomically. No lost update: the locked read+UPSERT are one txn. |
| **R6** | `POST /balances/rebuild` scoped to `(org)` / `(org, area)` / `(org, area, year)` | `(optional) financial_area FOR SHARE` → `(optional) fiscal_year FOR SHARE` → **`account_balance_projections SCOPE slice FOR UPDATE ASC (all rows matching predicate)`** → `DELETE` scoped slice → `SELECT SUM(debit/credit) FROM ledger_entries WHERE scope GROUP BY key HAVING <>0` (ledger-group aggregation) → `INSERT` batch of new rows | SHARE/UPDATE/DELETE/SELECT/INSERT | Slice is frozen while aggregation reads ledger — a concurrent finalize whose key falls in the slice waits on the slice rows; a key outside the slice proceeds. Rebuild is **idempotent-by-replacement** (AC-I-19e): running it twice yields identical rows (deterministic `GROUP BY`). No account row held concurrently, so a concurrently closing year (needs year lock) serializes on area/year before reaching balances — order never inverts. |
| **R7** | Finalize concurrent with rebuild overlapping slice | Finalize: `area→year→period → accounts FOR SHARE → balances FOR UPDATE (touched keys)` — **but rebuild already holds `balances FOR UPDATE` for the whole slice**, so finalize's per-key waits block; Rebuild: holds slice `FOR UPDATE` then reads ledger. **Winner is whichever grabbed the slice/key first — loser waits, then sees winner's COMMIT.** | Mixed | AC-I-19 correctness:rebuild's `SELECT` is ledger-truth; finalization's turnover always wins because it produces both ledger rows and the matching balance delta. No interleaving where ledger has a row whose turnover is missing from balances. |
| **R8** | Reads: `GET /balances`, `GET /balances/:accountId`, `GET /balances/reconciliation` | **No locks** — `accounting.account_balance_projections` reads via Prisma `findMany` / view `vw_balance_reconciliation` via `$queryRaw`; ledger aggregate via `GROUP BY` / view | (no) | Read-only paths must never wait. Consistency is "read committed": concurrently-finalizing voucher's balances become visible only after its COMMIT (along with its ledger rows). |

## 3. Cross-Cutting Notes

- **Sort & dedup discipline:** every multi-row lock input is deduplicated (`Set`) + sorted ascending by id before the loop. Callers that pass `accountId`s from voucher lines or projection keys from ledger deltas apply this before the first `SELECT … FOR SHARE/UPDATE` in that transaction — the per-transaction loop then awaits each `SELECT` sequentially (never `Promise.all` across `FOR` queries), so the hold order is deterministic.

- **Idempotency row placement:** `accounting_posting_operations` is always the **last** `INSERT` of any `accounting.*` transaction (`createChecked`, `finalizeChecked`, and the future correction task). A lost `operation_key` race therefore aborts the whole transaction; the loser re-reads via `findByKey` and replays the winner's stored result — never creating a second effect (AC-I-12, §16.4). This placement is unchanged by Task 12's added balance `UPSERT` — the operation row stays LAST even after the new tail.

- **Prisma migration drift risk:** no `CHECK` constraints, no triggers, no partial unique indexes visible to Prisma are introduced for this invariant — Prisma cannot represent them, and the next `prisma migrate dev` would silently `DROP` them (the reason `is_active` / lifecycle rules are domain-enforced and the "exactly one ACTIVE version per org" guarantee is tested in `test/accounting-configuration-live.e2e-spec.ts` + the rehearsal). The Task-12 migration's raw partial index for the one-ACTIVE guarantee is carried deliberately with a test-rehearsed exemption (Task 11 pattern).

- **Operational-usage marker (Task 13):** `accounting_configuration.operationally_used_at` is written by exactly one statement, inside `finalizeChecked` at the configuration position of the global order (row D4″). Two rules hold it in place: (a) it is a *side effect* of a committed business operation, never an operation of its own — adding a route, a permission or a "mark the ACTIVE configuration" heuristic would let a caller freeze a configuration without doing anything (and reopen the DoS-by-edit vector `ensureConfigurationMutable` exists to close); (b) it must stay *before* the account locks and *before* any ledger insert, so it never holds a ledger or balance lock while waiting for a configuration, and it agrees with the chart's configuration-before-account order (`A1`, `A5`). A new writer of that column must update this note and the `D4″` row with it.

- **Documentation obligation (AG-07/AR-11):** this file is the canonical concurrency reference for Accounting writes. Any new `SELECT … FOR` lock or any change that moves a lock earlier/later must update this matrix **and** the header of `backend/src/modules/accounting/data/accounting-locks.ts` in the same PR, and must keep the "never reversed" order — especially the Tail position of `account_balance_projections` between accounts and the document.
